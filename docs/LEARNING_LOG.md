### 本次学习材料要点

1. **里程碑与任务不同。** 任务是具体实现动作，里程碑是可展示的结果。例如 P4 的解析、分块、向量入库是任务；P5 出口的“上传文档后可问答并定位引用”才是知识库闭环。
2. **按依赖推进。** RAG 需要先有文档、分块、Embedding 和检索；Agent 需要先有真实模型与受控工具。先建设这些基础，错误出现时更容易定位。
3. **模块化单体不等于所有代码放在一个文件。** 计划让 API、模型、知识库、工具和工作流各自承担明确职责，耗时任务由独立 worker 执行；暂不承担微服务通信与部署复杂度。
4. **设计、实现与验证是三种状态。** 写出架构不代表功能可运行，写出函数不代表正确；缺少真实依赖验证时要说明限制。
5. **完整项目要覆盖故障路径。** 上传失败、模型超时、工具越权、worker 重启和备份恢复，都属于实际产品行为。

### 为什么这样规划及可选方式

当前选择本地单组织、逐阶段形成完整链路，便于学习和验证。也可以先做演示原型，或从首版开始建设多租户与微服务；前者容易遗漏权限与恢复，后者会增加早期复杂度。这里按用户确认的首版范围安排，不把未来需求提前全部实现。

### 常见错误与面试考察方向

- 常见错误：将路线图勾选为已实现；先做复杂 Agent 再补底层检索；只测成功响应；以单元测试替身冒充真实模型或 MCP；把内存状态当持久化。
- 面试可能要求：解释为何选择模块化单体；说明一份文档如何从上传进入 RAG 上下文；解释 API、worker、数据库和 Redis 的职责；说明为什么检查点不能保证外部工具只执行一次。

## 2026-11-09：第二课——Docker 环境、真实故障恢复与持久化

状态：已结合实际运行提供讲解与练习，**待用户回答、待独立实践验证**。本次是代理完成的配置与验收，不能作为用户已掌握的证据。

对应代码：compose.yaml、Dockerfile、docker/postgres/init-vector.sql、scripts/verify_p1.py；对应证据见 [P1 验收记录](acceptance/P1_2026-11-09.md)。完整流程、设计理由、替代方案、常见错误、面试方向及练习统一放在 [基础模块第二课](modules/FOUNDATION.md)。

学习要点：

- Windows 的 Docker Desktop 通过 WSL 2 运行 Linux 容器，CLI、引擎、Compose 和凭据助手各有职责；安装后的旧进程 PATH 不会自动刷新。
- Compose 服务发现使用内部服务名；容器内 localhost 指自己。仅发布 API 的回环端口，数据库/Redis 保留内部网络边界。
- live 与 ready 在真实停止依赖后表现不同；恢复时 API ID 保持不变，证明无需重启 API 即可重新就绪。
- 命名卷独立于容器；同时核对容器 ID 变化与相同数据保留，才能证明不是只重启原容器。Redis AOF 配置及实际数据读取共同验证恢复。
- 正常 stop/down/up 不等于断电恢复，命名卷也不等于独立备份。临时测试 schema/键只由验收脚本创建和清理，不作为业务数据库设计。

练习安排：3 个理解题、1 个脚本增加 AOF 配置断言的代码任务、1 个未来数据库与文件卷一致性备份的思考题。尚未收到回答或独立修改，不标记已掌握。
